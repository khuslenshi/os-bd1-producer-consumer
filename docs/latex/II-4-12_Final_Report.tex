\subsection{Item шалгалт}
БД1-ийн invariant нь зөвхөн тоолуурыг харьцуулдаг: \code{produced - consumed == count}. Mutex-гүй үед хоёр producer нэг нүд рүү бичээд, хоёр consumer нэг нүдийг уншвал алдагдсан ба давхар авсан item-ууд бие биенээ нөхөж, тэнцэл санамсаргүйгээр биелж болно (II-4-7-ийн X3 туршилт). Иймд тавьсан item бүрт дугаар өгч, нүд бүрт хадгална. Авахдаа тухайн дугаарыг "авсан" гэж тэмдэглээд нүдийг 0 болгоно.

\begin{lstlisting}[title={\textbf{Код 1.} Дугаартай \texttt{insert\_item}, \texttt{remove\_item} (src/core/pc.c, товчилсон)}]
static int insert_item(buffer_item item, int *slot) {
    if (count >= bsize) return -1;
    *slot = in_idx;
    buffer[in_idx] = item;
    ids[in_idx] = __atomic_add_fetch(&next_serial, 1, __ATOMIC_RELAXED);
    SET(in_idx, (in_idx + 1) % bsize);
    SET(count, count + 1);
    return 0;
}
static int remove_item(buffer_item *item, int *slot) {
    if (count <= 0) return -1;
    *slot = out_idx;
    *item = buffer[out_idx];
    long serial = ids[out_idx];
    ids[out_idx] = 0;
    if (serial == 0) ghost_reads++;            /* atomic in the code */
    else seen[serial]++;                       /* atomic in the code */
    SET(out_idx, (out_idx + 1) % bsize);
    SET(count, count - 1);
    return 0;
}
\end{lstlisting}

Төгсгөлд дугаар бүрийг шалгана: хэн ч аваагүй, буферт ч байхгүй бол \textbf{алдагдсан} (\code{lost}), нэгээс олон удаа авсан эсвэл хоосон нүдийг уншсан бол \textbf{давхар} (\code{dup}). Зөв синхрончлолтой үед хоёулаа 0. \code{in\_idx}, \code{count}-ийн шинэчлэл нь зориуд "уншаад, бичих" хэвээр: mutex-гүй үед хоёр thread шинэчлэлээ алдах боломж хадгалагдаж, race-ийн жишээ ажилласаар байна.

\subsection{Atomic snapshot ба зогсоох флаг}
Log мөр бүр бусад thread-ийн mutex дотор өөрчилдөг \code{in}, \code{out}, \code{count}, \code{empty}, \code{full}, mutex эзэмшигчийг уншдаг. БД1-д эдгээрийг энгийн хувьсагчаар уншдаг байсан нь C стандартаар data race. Одоо \code{SNAP(x)} (\code{\_\_atomic\_load\_n}) ба \code{SET(x, v)} (\code{\_\_atomic\_store\_n}) ашиглана. Зогсоох флаг \code{running}-ийг main thread болон signal handler бичиж, бүх thread уншдаг тул мөн atomic болгосон (lock-free atomic store нь signal handler-т аюулгүй).

\subsection{Thread үүсгэх алдаа}
\code{pthread\_create} амжилтгүй бол (санах ой, thread-ийн хязгаар) үлдсэн thread-ийг үүсгэхээ зогсоож, бусдыг зогсоож, зөвхөн үүссэн thread-үүдийг \code{join} хийгээд "thread үүсгэж чадсангүй (Resource temporarily unavailable), 400-аас N нь үүссэн" гэж тайлбарлан 1 кодоор гарна.

\subsection{Ажиглалтын урсгал}
\begin{enumerate}
  \item Start дарахад core эхэлж, үйлдэл бүр Stage-д (thread карт, буфер, сум), timeline-д, event log-д тоглогдоно.
  \item Буфер дүүрэхэд producer шар (\code{empty = 0}), хоосрох үед consumer шар (\code{full = 0}) болж хүлээнэ. Mutex эзэмшигч хар хүрээтэй.
  \item Mutex-гүй үед \code{count} хүлээгдсэн утгаасаа зөрсөн \code{produce}/\code{consume} улаанаар тэмдэглэгдэж, "count = 2, 1 байх ёстой" гэх тайлбар гарна.
  \item Төгсгөлд хоёр шалгалт: \textbf{Invariant} (тавьсан - авсан = үлдсэн) ба \textbf{Item} (алдагдсан, давхар).
\end{enumerate}

\section{Дүгнэлт}

\textbf{Эцсийн үнэ цэнэ.} Producer-Consumer бодлогыг сурах бичгийн дагуу бодит C программаар шийдэж, түүний thread бүрийн үйлдлийг дүрслэх интерфейсээр харуулсан. БД2-т шүүмжийн дагуу race-ийн нотолгоог бэхжүүлсэн: mutex-гүй үед юу буруу болсныг тоолуураар төдийгүй алдагдсан ба давхар авсан item-ээр харуулдаг болсон. Mutex-тэй горим ThreadSanitizer-ийн шалгалтыг цэвэр давж, dependency-ийн эмзэг байдал арилж, Manual өөр Linux орчинд эхний алхмаасаа ажиллахуйц болов.

\textbf{Суралцсан зүйл.}
\begin{itemize}
  \item Тоолуурын тэнцэл (invariant) нь синхрончлолын алдааг найдвартай илрүүлэхгүй: алдаанууд бие биенээ нөхөж болно. Өгөгдлийн нэг бүрчлэн шалгалт (item дугаар) илүү хүчтэй нотолгоо.
  \item "Зөвхөн log-д уншдаг" хувьсагч ч C стандартаар data race. ThreadSanitizer үүнийг ил гаргаж, atomic уншилт нь шийдлийг тодорхой болгосон.
  \item Шүүмжлэгч өөр орчинд (x86\_64 Linux) ажиллуулахад бидний Mac дээр харагдаагүй асуудал (invariant 8/8 таарах, Node суугаагүй) гарч ирсэн. Олон орчны CI ба шинэ хэрэглэгчийн нүдээр бичсэн Manual хэрэгтэй.
  \item Санал бүрийг шууд хэрэгжүүлэх биш, хүрээ, өртгөөр нь шийдэх: хэсэгчлэн зөвшөөрсөн, татгалзсан шийдвэр бүрт техникийн үндэслэл бичсэн.
\end{itemize}
