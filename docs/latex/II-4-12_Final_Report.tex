\section{Төслийн тойм}

\subsection{Зорилго ба ач холбогдол}
Төслийн зорилго нь сурах бичгийн 7-р бүлгийн Programming Project 4 "The Producer-Consumer Problem"-ийг бодит олон \term{thread}-тэй программаар хэрэгжүүлж, хэрэглэгч \term{thread}-ийн тоо, буферийн хэмжээ, унтах хугацааг өөрчлөн туршихад синхрончлолын механизм хэрхэн ажилладгийг нүдээр харж болохуйц болгох явдал юм [1]. Бие даалт 2-ын зорилго нь Бие даалт 1-ийн ажилд ирсэн шүүмжийг ангилж, зөвшөөрсөн саналыг хэрэгжүүлэн, засварын үр дүнг дахин туршилтаар нотлох явдал байв.

Producer-Consumer бодлого нь үйлдлийн системд гарын товчлуурын буфер, хэвлэгчийн дараалал, процесс хоорондын \term{pipe} зэрэг олон газар ашиглагддаг сонгодог синхрончлолын бодлого [1]. Dijkstra-гийн нөөцийн тоог тоолох хэрэгсэл болгон анх санал болгосон \term{semaphore}-ын хэрэглээний гол жишээ нь чухам энэ бодлого юм [3]. Олон \term{thread}-ийн алдаа давтагдахгүй, нүдэнд харагддаггүй тул бодит программын үйлдлийг алхам бүрээр харуулах нь ойлголтыг хөнгөвчилдөг бол \term{race condition}-ийг санаатайгаар үүсгэж, тоон үзүүлэлтээр илрүүлэх нь зөв синхрончлолын ач холбогдлыг тодорхой харуулдаг.

\subsection{Сурах бичгийн шаардлага ба Бие даалт 1-ийн үр дүн}
Project 4 нь тогтмол хэмжээтэй тойрог буфер, түүнд хандах \code{insert\_item()} ба \code{remove\_item()} функц, санамсаргүй хугацаагаар унтаад тоо тавих producer ба авах consumer \term{thread}, ажиллах хугацаа, producer ба consumer-ийн тоо гэсэн гурван аргумент авах \code{main()} функцийг шаарддаг. Буфер дүүрэх, хоосрохыг \code{empty} ба \code{full} тоолох \term{semaphore}, буферийг өөрчлөх хэсгийг \term{mutex} хамгаална [1], [2].

Бие даалт 1-д (v1.0.11) эдгээр шаардлагыг бүрэн хангаж, дээр нь \code{--buffer}, \code{--sleep-max}, \code{--seed}, \code{--no-mutex} сонголт, бодит программын үйлдлийг шууд дамжуулдаг Next.js интерфейс, дуут хичээл, асуулттай гурван түвшин, 18 автомат тест ба Ubuntu, macOS орчны CI-г нэмсэн.

\subsection{Шүүмж ба Бие даалт 2-ын хамрах хүрээ}
Бие даалт 1-ийн постонд хоёр баг албан ёсны шүүмж бичсэн. II-4-7 баг 2026 оны 11 дүгээр сарын 1-нд Ubuntu 24.04 (x86\_64), V-1-8 баг 11 дүгээр сарын 8-нд Debian 13 (x86\_64) орчинд Manual-ийн дагуу программыг ажиллуулж, үндсэн тест бүгд амжилттай, Critical түвшний асуудал байхгүй гэж баталсан. Бие даалт 2-т хоёр шүүмжийн давхардлыг нэгтгэсэн 14 саналыг шийдвэрлэж, кодын өөрчлөлт, дахин туршилт, Manual, README, постерийг эцэслэв.

\subsection{Item шалгалт}
Бие даалт 1-ийн программ төгсгөлд нь "тавьсан - авсан = буферт үлдсэн" гэсэн тэнцлийг шалгадаг байсан. II-4-7 баг \term{mutex}-гүй 8 ажиллалтын 8-д нь энэ тэнцэл биелсэн атлаа лог дотор \term{race condition} тодорхой харагдаж байсныг тэмдэглэсэн. Учир нь хоёр producer нэг нүд рүү зэрэг бичихэд нэг \term{item} алдагдаж, хоёр consumer нэг нүдийг уншихад нэг \term{item} давхар авагддаг ч эдгээр алдаа тоолуур дээр бие биеэ нөхөж болдог. Иймд тоолуурыг бус \term{item} бүрийг шалгах аргыг сонгов (Зураг~\ref{fig:items}).

Producer \term{item} тавихдаа нүдэнд нь давтагдашгүй дугаар бичиж, consumer авахдаа тэр дугаарыг "авсан" гэж тэмдэглээд нүдийг хоосолно (Код~1). Программ дуусахад дугаар бүрийг зөв, алдагдсан, давхар гэсэн гурван бүлэгт хуваахад синхрончлол зөв бол сүүлийн хоёр бүлэг хоосон гарах ёстой.

\begin{lstlisting}[title={\textbf{Код 1.} Дугаартай \texttt{insert\_item}, \texttt{remove\_item} (src/core/pc.c, товчилсон)}]
static int insert_item(buffer_item item, int *slot) {
    if (count >= bsize) return -1;
    *slot = in_idx;
    buffer[in_idx] = item;
    ids[in_idx] = __atomic_add_fetch(&next_serial, 1, __ATOMIC_RELAXED);
    SET(in_idx, (in_idx + 1) % bsize);
    SET(count, count + 1);
    return 0;
}
static int remove_item(buffer_item *item, int *slot) {
    if (count <= 0) return -1;
    *slot = out_idx;
    *item = buffer[out_idx];
    long serial = ids[out_idx];
    ids[out_idx] = 0;
    if (serial == 0) ghost_reads++;      /* atomic in the code */
    else seen[serial]++;                 /* atomic in the code */
    SET(out_idx, (out_idx + 1) % bsize);
    SET(count, count - 1);
    return 0;
}
\end{lstlisting}

Код 1-д \code{in\_idx} ба \code{count}-ийн шинэчлэл нь зориуд "уншаад, дараа нь бичих" хоёр алхамтай хэвээр үлдсэнээр \term{mutex}-гүй горимд хоёр \term{thread} шинэчлэлээ алдах боломж хадгалагдаж, \term{race condition}-ийн жишээ ажилласаар байна.

\subsection{Атомар уншилт ба алдааны боловсруулалт}
V-1-8 баг ThreadSanitizer хэрэгслээр шалгахад \term{mutex}-тэй горимд ч 29-31 анхааруулга гарсан. Лог мөр бүр бусад \term{thread}-ийн \term{mutex} дотор өөрчилдөг \code{in}, \code{out}, \code{count}, \code{empty}, \code{full}-ийг энгийн хувьсагчаар уншдаг байсан нь C хэлний стандартаар \term{data race} буюу тодорхойгүй үйлдэл юм [4], [5]. Эдгээр уншилт болон зогсоох флагийг C11 стандартын атомар үйлдлээр [6] (\code{\_\_atomic\_load\_n}, \code{\_\_atomic\_store\_n}) сольсон нь дохио боловсруулагчаас ч аюулгүй бичих боломж олгож, \code{SIGTERM} ирэхэд программ зөв зогсох нөхцөлийг бүрдүүлсэн.

\code{pthread\_create} амжилтгүй болбол (санах ой эсвэл \term{thread}-ийн хязгаар хүрэх) программ шинэ \term{thread} үүсгэхээ зогсоож, зөвхөн үүссэн \term{thread}-үүд дуусахыг хүлээгээд ойлгомжтой тайлбартайгаар 1 кодоор гардаг болсон [2]. Маршрут талд өөр сайтын хуудаснаас ирсэн хүсэлтийг \code{Sec-Fetch-Site}-аас гадна \code{Origin} толгойгоор татгалздаг болсон.

Ижил \code{seed} нь \term{thread} бүрийн унтах хугацааг давтах боловч үйлдлийн дараалал үйлдлийн системийн төлөвлөгчөөс хамаарч өөр байж болно.

\subsection{Ажиглалтын урсгал}
Ажиллалт эхлэхэд дэлгэц үйлдэл бүрийг тоглуулж, \term{thread}-ийн төлөвийг өнгөөр ялгана. Хэрэглэгч дараах дарааллаар ажиглана:
\begin{enumerate}
  \item Буфер дүүрэхэд (\code{empty = 0}) producer-ийн карт шар болж хүлээгээд consumer нэг \term{item} авмагц сэрж тавина (Зураг~\ref{fig:full}).
  \item Буфер хоосон үед (\code{full = 0}) consumer-ууд шар болж хүлээнэ.
  \item Нэг мөчид зөвхөн нэг \term{thread} \term{mutex} эзэмшиж, хар хүрээтэй харагдана.
  \item \term{Mutex}-гүй үед \code{count} нь хүлээгдсэн утгаасаа зөрсөн үйлдэл улаанаар тэмдэглэгдэнэ.
  \item Ажиллалтын төгсгөлд тэнцлийн ба \term{item}-ийн шалгалтын үр дүн гарна.
\end{enumerate}
Эхний гурван алхам нь \term{semaphore} ба \term{mutex} зөв ажиллаж буйг, сүүлийн хоёр нь хамгаалалтгүй үеийн алдааг харуулдаг.

\section{Хязгаарлалт}

Засварын дараа ч программд дараах хязгаарлалт үлдсэн. Эдгээрийг Manual, README-ийн "Known issues" хэсэгт мөн бичсэн:
\begin{itemize}
  \item \term{Mutex}-гүй үед \term{race} магадлалтай: 30 ажиллалтын 2-3-т \term{race} гарсан ч \term{item} алдагдаагүй, тоолуур зөрөөгүй тул төгсгөлийн шалгалт илрүүлдэггүй. Ийм ажиллалтад зөвхөн алхам бүрийн \code{count} шалгалт үлдэнэ.
  \item \term{Mutex}-гүй үед лог дахь дараалал бодит дараалалтай яг таарахгүй, ThreadSanitizer-ийн \term{data race} мэдээлэл ч энэ горимд зориуд гарна.
  \item \term{Item} шалгалт эхний 16 777 216 \term{item}-ийг шалгана (унтах 0 үед 100 секунд орчим).
  \item Хүлээх үйлдэл \term{thread} блоклогдох гэж буй агшинд хэвлэгддэг ч хүлээлтийн төгсгөл тусдаа үйлдлээр гардаггүй.
  \item Өөр сайтын хүсэлтийн шалгалт нь нэвтрэлтийн механизм биш, зөвхөн хөтчийн хамгаалалт.
\end{itemize}
Эдгээр нь \term{mutex}-гүй жишээний хэмжилтийн нарийвчлал, хэрэглээний хүрээг хязгаарлах болохоос программын үндсэн ажиллагаа буюу зөв синхрончлолд нөлөөлөхгүй.

Программыг macOS, Linux дээр шууд, Windows дээр WSL2 эсвэл virtual machine доторх Linux-аар ажиллуулахад Node.js 22.18 буюу түүнээс дээш хувилбар, C compiler ба \code{make}, тестэд Python 3 шаардлагатай. II-4-7, V-1-8 баг x86\_64 Linux дээр, CI нь Ubuntu ба macOS дээр, баг Apple Silicon macOS дээр туршсан тул эдгээр орчинд ажиллагаа нотлогдсон.

\section{Дүгнэлт}

Энэхүү ажлаар Producer-Consumer бодлогыг сурах бичгийн дагуу бодит C программаар шийдэж, түүний \term{thread} бүрийн үйлдлийг дүрслэх интерфейсээр харуулсан. Бие даалт 2-т шүүмжийн дагуу \term{race condition}-ийн нотолгоог бэхжүүлсэн: \term{mutex}-гүй үед юу буруу болсныг тоолуураар төдийгүй алдагдсан ба давхар авсан \term{item}-ээр харуулдаг болов. \term{Mutex}-тэй горим ThreadSanitizer-ийн шалгалтыг анхааруулгагүй давж, гадны сангийн эмзэг байдал арилж, Manual нь шинэ Linux орчинд эхний алхмаасаа ажиллахуйц болсон.

Ажлын явцад хэд хэдэн зүйлийг ойлгосон. Алдаанууд бие биеэ нөхөж болдог учраас тоолуурын тэнцэл синхрончлолын алдааг найдвартай илрүүлэхгүй, харин өгөгдлийг нэг бүрчлэн шалгах нь илүү хүчтэй нотолгоо болдог. ThreadSanitizer-ийн үр дүнгээс зөвхөн лог хэвлэхэд уншдаг хувьсагч ч C стандартаар \term{data race} үүсгэдэг, түүнийг нүдээр бус багаж хэрэгслээр шалгах хэрэгтэйг ойлгосон [4], [5]. Шүүмжлэгч өөр орчинд ажиллуулахад манай Mac дээр харагдаагүй асуудал гарч ирсэн нь олон орчны туршилт, шинэ хэрэглэгчийн нүдээр бичсэн Manual-ийн ач холбогдлыг харуулав.
