\usection{Хураангуй}

\textbf{Асуудал.} Producer-Consumer буюу хязгаартай буферийн (bounded buffer) бодлогод хэд хэдэн thread нэг дундын буферт зэрэг хандана. Producer дүүрсэн буферт, consumer хоосон буферээс хандах ёсгүй бөгөөд буферийг өөрчлөх хэсэгт нэг зэрэг хоёр thread орвол өгөгдөл алдагдана (race condition).

\textbf{Шийдэл.} Сурах бичгийн Programming Project 4-ийн дагуу C хэл, POSIX thread (pthreads), \code{empty}, \code{full} counting semaphore болон mutex lock ашиглан тойрог буферийг хэрэгжүүлэв. Программ үйлдэл бүрээ JSON мөрөөр хэвлэнэ. Next.js вэб интерфейс уг программыг ажиллуулж, бодит үйлдлүүдийг шууд хүлээн авч, багшийн оноосон "Buffer animation" дүрслэлээр алхам алхмаар харуулна. Интерфейс нь тохиргоо, бэлэн туршилт, timeline, event log, дуут хичээл, асуулттай түвшингүүдийг агуулна.

\textbf{Туршилт.} C программыг 18 автомат тестээр (үндсэн, захын, буруу оролт, дохио), timeline загварыг 3 тестээр шалгаж, GitHub Actions дээр Ubuntu ба macOS орчинд push бүрт ажиллуулдаг болгосон. Интерфейсийг бэлэн гурван туршилтаар гараар туршив.

\textbf{Гол үр дүн.} 18/18 тест амжилттай. Mutex-тэй бүх ажиллалтад "тавьсан - авсан = буферт үлдсэн" тэнцэл (invariant) биелсэн. Mutex-гүй ажиллалтын 5-аас 5-д нь race condition илэрсэн бөгөөд жишээ нь 1 секундын ажиллалтад 8708 үйлдлээс 584 зөрчил гарч, интерфейс бүрийг нь улаанаар тэмдэглэж, нэг нэгээр нь үзүүлсэн.

\section{Удиртгал}

\subsection{Зорилго}
Сурах бичгийн 7-р бүлгийн Programming Project 4 "The Producer-Consumer Problem"-ийг хэрэгжүүлж, хэрэглэгч өөр өгөгдөл, параметрээр турших боломжтой программ бүтээх. Программын ажиллагааг багшийн оноосон "Buffer animation" дүрслэлээр харуулж, хэрэгжилт болон туршилтын үр дүнг баримтжуулах.

\subsection{Ач холбогдол}
Producer-Consumer нь синхрончлолын сонгодог бодлого бөгөөд үйлдлийн системд гарын товчлуурын буфер, принтерийн дараалал, pipe (\code{ls | grep}), сүлжээний пакетын буфер, видео урьдчилан ачаалах зэрэг олон газарт ашиглагддаг. Semaphore ба mutex-ийг зөв дарааллаар хэрэглэх, race condition-ийг таних нь зэрэгцээ программчлалын үндсэн чадвар юм. Thread-үүдийн ажиллагаа нүдэнд харагддаггүй тул бодит программын үйлдлийг дүрслэх нь ойлголтыг ихээхэн хөнгөвчилнө.

\subsection{Хамрах хүрээ}
\begin{itemize}
  \item C хэл дээрх producer/consumer thread, тойрог буфер, \code{empty}/\code{full} semaphore, mutex (сурах бичгийн үндсэн шаардлага).
  \item Mutex-гүй горимоор race condition-ийг санаатайгаар үүсгэж харуулах.
  \item Оролтыг шалгах, үйлдэл бүрийг JSON мөрөөр хэвлэх, дохиогоор (SIGTERM) зогсох.
  \item Бодит программтай шууд холбогдсон вэб интерфейс: тохиргоо, дүрслэл, timeline, event log, хичээл, түвшингүүд.
  \item Автомат тест, CI, хэрэглэгчийн ба operational гарын авлага (Manual).
\end{itemize}
Олон процесс (fork) хоорондын буфер, Windows API хувилбар хамрах хүрээнд ороогүй.

\section{Онолын үндэс}

\subsection{Critical section ба race condition}
Хэд хэдэн thread нэг дундын өгөгдлийг зэрэг өөрчлөх үед үр дүн нь гүйцэтгэлийн дарааллаас хамаарах нөхцөлийг race condition гэнэ. Буферт тавих үйлдэл нь "\code{buffer[in] = item}", "\code{in = (in + 1) \% n}", "\code{count++}" гэсэн хэд хэдэн алхмаас бүрдэх бөгөөд энэ хэсгийг critical section гэнэ. Хоёр producer зэрэг орвол нэг нүд рүү хоёулаа бичиж, нэг утга алга болох, \code{count} буруу болох аюултай. Critical section-ийн шийдэл нь харилцан гадуурхал (mutual exclusion), ахиц (progress), хязгаартай хүлээлт (bounded waiting) гэсэн гурван шаардлагыг хангах ёстой.

\subsection{Semaphore}
Semaphore нь бүхэл тоон утгатай хувьсагч бөгөөд зөвхөн хоёр атомар үйлдлээр хандана. \code{wait()} (POSIX: \code{sem\_wait}) утгыг 1-ээр хасна; утга 0 байвал thread блоклогдож хүлээнэ. \code{signal()} (\code{sem\_post}) утгыг 1-ээр нэмж, хүлээж буй thread байвал нэгийг сэрээнэ. Counting semaphore нь нөөцийн тоог хадгалдаг тул буферийн сул болон дүүрсэн нүдний тоог тоолоход тохиромжтой.

\subsection{Mutex lock}
Mutex нь нэг мөчид зөвхөн нэг thread-д critical section-д орох эрх олгоно (\code{pthread\_mutex\_lock}/\code{unlock}). Цоож барьсан thread л буферийг өөрчлөх тул \code{in}, \code{out}, \code{count} зөрөхгүй.

\subsection{Bounded buffer шийдэл}
Номын 7.1.1 хэсгийн шийдэл гурван синхрончлолын хувьсагч ашиглана: \code{mutex = 1}, \code{empty = n} (сул нүдний тоо), \code{full = 0} (дүүрсэн нүдний тоо). Producer-ийн бүтэц (номын Зураг 7.1):

\begin{lstlisting}[title={\textbf{Код 1.} Producer-ийн бүтэц (номын Зураг 7.1)}]
while (true) {
   /* produce an item in next_produced */
   wait(empty);
   wait(mutex);
   /* add next_produced to the buffer */
   signal(mutex);
   signal(full);
}
\end{lstlisting}

Consumer нь тэгш хэмтэй: \code{wait(full)}, \code{wait(mutex)}, авах, \code{signal(mutex)}, \code{signal(empty)}. \code{empty} нь буфер дүүрэх үед producer-ийг, \code{full} нь хоосон үед consumer-ийг зогсооно. Mutex нь зөвхөн буферийг өөрчлөх богино хэсгийг хамгаална.

\subsection{Тойрог буфер}
Буфер нь \code{n} нүдтэй массив, хоёр заагчтай: \code{in} нь дараагийн тавих нүд, \code{out} нь дараагийн авах нүд. Заагч бүр \code{(i + 1) \% n}-ээр урагшилж, сүүлийн нүдний дараа 0 руу эргэнэ. Иймээс анх тавьсан нь анх авагдана (FIFO).

\subsection{Invariant}
Зөв синхрончлолтой ажиллалтын төгсгөлд "тавьсан тоо - авсан тоо = буферт үлдсэн тоо" ба \code{0 <= count <= n} үргэлж биелнэ. Энэ тэнцлийг программ төгсгөлд нь шалгаж (\code{invariant\_ok}), тест болон интерфейс зөв ажиллагааны нотолгоо болгон ашиглана.

\subsection{C core: буфер}
Номын API-г хадгалж, тойрог буферийг дараах байдлаар хэрэгжүүлэв. Функцүүд mutex дотроос дуудагдана.

\begin{lstlisting}[title={\textbf{Код 2.} \texttt{insert\_item} ба \texttt{remove\_item} (src/core/pc.c)}]
static int insert_item(buffer_item item, int *slot) {
    if (count >= bsize) return -1;
    *slot = in_idx;
    buffer[in_idx] = item;
    in_idx = (in_idx + 1) % bsize;
    count++;
    return 0;
}

static int remove_item(buffer_item *item, int *slot) {
    if (count <= 0) return -1;
    *slot = out_idx;
    *item = buffer[out_idx];
    out_idx = (out_idx + 1) % bsize;
    count--;
    return 0;
}
\end{lstlisting}

\subsection{C core: producer ба consumer}
Producer санамсаргүй унтаад (\code{rand\_r}, thread бүр seed-ээс гарган авсан өөрийн төлөвтэй, ижил seed = ижил унталт), 0-99 тоо үүсгэнэ. Хүлээлтийг интерфейст харуулахын тулд эхлээд \code{sem\_trywait}-ээр оролдож, амжилтгүй бол \code{wait\_empty} үйлдэл хэвлээд жинхэнэ \code{sem\_wait}-ээр блоклогдоно. Дараа нь mutex барьж буферт тавина.

\begin{lstlisting}[title={\textbf{Код 3.} Producer-ийн гол хэсэг (src/core/pc.c, товчилсон)}]
if (sem_trywait(sem_empty) != 0) {      /* buffer full -> will block */
    emit("wait_empty", "producer", id, item, -1, -1);
    sem_wait_retry(sem_empty);
}
if (use_mutex) { pthread_mutex_lock(&mutex); mtx_owner = id; }
if (insert_item(item, &slot) == 0)
    emit("produce", "producer", id, item, slot, -1);
if (use_mutex) { mtx_owner = 0; pthread_mutex_unlock(&mutex); }
sem_post(sem_full);
\end{lstlisting}

Consumer нь \code{full} дээр хүлээж, \code{remove\_item}-ээр авч, \code{sem\_post(empty)} хийнэ. \code{--no-mutex} сонголтоор mutex-ийг алгасаж race condition-ийг санаатайгаар үүсгэнэ. Бусад шийдэл:
\begin{itemize}
  \item macOS нэргүй semaphore (\code{sem\_init}) дэмждэггүй тул \code{\#ifdef \_\_APPLE\_\_} үед \code{sem\_open} ашиглана. \code{sem\_getvalue} macOS дээр ажиллахгүй тул \code{empty}/\code{full}-ийн утгыг semaphore-той зэрэг атомар тоолуураар хадгална.
  \item Хэвлэлтийг тусдаа \code{log\_mutex}-ээр хамгаалж мөрүүд холилдохгүй. \code{produce}/\code{consume} нь mutex дотроос хэвлэгддэг тул mutex-тэй үед лог дахь дараалал нь буферт болсон бодит дараалал.
  \item \code{SIGINT}/\code{SIGTERM}-д \code{running = 0} болгож, блоклогдсон thread-үүдийг \code{sem\_post}-оор сэрээж, \code{pthread\_join}-оор хүлээгээд, \code{end} мөрөнд invariant-ийг хэвлэнэ.
  \item Аргумент бүрийг хүрээгээр шалгаж (жишээ нь буфер 1-64), алдаатай бол Монгол хэлээр тайлбар, хэрэглээний заавар хэвлээд 1 кодоор гарна.
\end{itemize}

\section{Хэлэлцүүлэг}

\subsection{Үр дүнгийн тайлбар}
Mutex-тэй бүх тест, тэр дундаа унтах хугацаа 0 (66337 үйлдэл) ба 100+100 thread гэх мэт хамгийн их contention-тэй нөхцөлд invariant биелсэн нь semaphore ба mutex-ийн хослол буферийг зөв хамгаалж байгааг харуулна. Producer олон үед \code{empty} (T2: 48 хүлээлт), consumer олон үед \code{full} (T3: 55 хүлээлт) semaphore thread-үүдийг зогсоож байгаа нь интерфейс дээр шар картаар шууд харагдана. Mutex-гүй үед race тогтмол гарч, зарим ажиллалтад төгсгөлийн invariant ч зөрөх боломжтой нь "lost update"-ийн бодит жишээ юм.

\subsection{Хүлээх дараалал ба deadlock}
Producer эхлээд \code{wait(empty)}, дараа нь \code{wait(mutex)} хийх ёстой. Хэрэв дарааллыг солиод mutex-ийг барьсан чигтээ дүүрэн буфер дээр \code{wait(empty)} хийвэл consumer mutex авч чадахгүй тул хэн ч урагшлахгүй (deadlock). Манай хэрэгжилт номын дарааллыг баримталсан тул ийм гацаа гарахгүй. Мөн mutex-ийг зөвхөн буферийг өөрчлөх богино хэсэгт барьж, унталт ба хүлээлтийг critical section-ээс гадуур хийсэн.

\subsection{Хязгаарлалт}
\begin{itemize}
  \item Хүлээлтийг \code{sem\_trywait}-ээр урьдчилан илрүүлдэг тул \code{wait\_*} үйлдэл нь "блоклогдох гэж байна" гэсэн утгатай; маш богино хугацаанд сэрвэл хүлээлт бараг харагдахгүй.
  \item Mutex-гүй үед лог дахь дараалал найдваргүй тул race-ийг зөвхөн \code{count}-ын зөрүүгээр илрүүлдэг; нэг агшинд хэд хэдэн thread давхцсан ч нэг race гэж тоологдож болно.
  \item Нэг ажиллалт хамгийн ихдээ 20000 үйлдэл; маш олон үйлдэлтэй ажиллалтыг (Түвшин 3) нүдээр хөөх боломжгүй тул интерфейс анхааруулга гаргаж, race-уудыг нэг нэгээр нь үзүүлнэ.
  \item Интерфейсийн хязгаар (thread 16, буфер 16) core-оос (thread 200, буфер 64) нарийн.
\end{itemize}
